# Kova — Pre-Release Audit (Round 2)

A second whole-app audit ahead of launch, run as 11 specialized auditors (security & tenancy, money paths, AI suite, UI consistency, feature completeness, frontend correctness, data integrity, domain math, accessibility/PWA, ops/release, build/test health) followed by an adversarial verification pass — every High/Critical finding was independently re-traced by two skeptics (correctness + real-world-impact), every Medium by one. Only findings that survived refutation are listed here.

**Bottom line:** the foundations audited in Round 1 (AUDIT.md) all held and have not regressed — tenant row-level isolation, the credit meter, webhook dedup, atomic redemptions, RBAC scoping, `isPlatformAdmin` fail-closed. Typecheck is clean and the test suite is green (187 domain + 150 API, up from the 96+83 CLAUDE.md still claims). The new findings cluster in **the Stripe rail, first-deploy/ops safety, AI spend controls, offline/PWA gaps, a repeated frontend timezone bug, and accessibility** — none are in the core money-meter or isolation invariants, but several are launch-blockers.

## Verdict

- **0 Critical · 15 High · 33 Medium** confirmed findings (plus 34 Low/minor).
- **Not release-ready as-is.** No data-loss or cross-tenant breach in the core paths, but the launch-blockers below (Stripe Connect rail, auth-secret fallback, mock-lane billing, broken staff invite, offline-first absence) must be resolved first.

Status legend: severity is post-verification. Every item was code-traced; file:line points at the confirmed defect.

## High (15)

### H1. Core coach navigation (client roster, plan list, inbox items) is click-only Card divs — unreachable by keyboard and unnamed to screen readers
**Area:** Accessibility & PWA — `apps/app/src/screens/coach/Clients.tsx:60`  
Card renders a plain <div> (packages/ui/src/primitives.tsx:120-133 — no role, no tabIndex, no key handler), and the only way to open a client is `<Card key={c.id} interactive onClick={() => nav(`/clients/${c.id}/today`)} ...>` (Clients.tsx:60). Same pattern for opening a plan: `<Card key={p.id} interactive onClick={() => open(p.id)} ...>` (CoachPlans.tsx:75) and opening a notification: `<Card key={n.id} onClick={() => void open(n)} ...>` (Inbox.tsx:79). There is no alternate route into ClientDetail — Shell.tsx routes /clients/:clientId only via this roster. Failure scenario: a keyboard-only or switch-access coach tabs through the Clients screen, focus never lands on any roster row (divs are not focusable), and they cannot open any client, any plan, or any inbox notification — the entire coaching surface behind the roster is inaccessible. Screen readers likewise announce nothing interactive.

**Fix:** Make Card render a <button> (or add role="button", tabIndex={0}, and Enter/Space key handling) when onClick/interactive is set, or wrap these three call sites' content in a real button/Link. The rest of the app already uses <button> rows correctly (e.g. NotificationBell.tsx:102, FoodSearchSheet FoodResult).

### H2. No safe-area-inset-top handling: app bar and full-screen plan headers render under the iOS status bar/notch in the installed PWA
**Area:** Accessibility & PWA — `packages/ui/src/shell.tsx:40`  
index.html sets `viewport-fit=cover` and the manifest sets `display: "standalone"`, so in the installed iOS app the layout extends under the status bar. But the AppBar is `<header className="sticky top-0 z-30 flex h-16 ... px-4">` with no `env(safe-area-inset-top)` padding (shell.tsx:40), and the WorkoutPlayer/MealPlanDrawer full-screen overlay headers are the same: `"sticky top-0 z-20 flex ... px-4 py-3"` (WorkoutPlayer.tsx:414, MealPlanDrawer.tsx:223). Failure scenario: install the PWA on any notched iPhone, open it — the tenant logo, help/bell/avatar buttons, and the workout player's Back button sit directly under the clock/notch, partially obscured and hard to tap, on every screen. The codebase demonstrably knows the pattern (BodyScanFlow.tsx:160 and media.tsx:43 use `pt-[calc(0.75rem+env(safe-area-inset-top))]`) but the two most-used chrome surfaces omit it. Note BottomTabs correctly pads the bottom inset (shell.tsx:58).

**Fix:** Add `pt-[env(safe-area-inset-top)]` (with the height accounting for it) to AppBar and to the sticky headers in PlanShell/MealPlanDrawer — mirroring what BodyScanFlow already does.

### H3. Mock AI lane can activate silently in production and charges real credits for fabricated output
**Area:** AI Suite — `apps/api/src/ai.ts:424`  
generate()/generateImage()/generateSpeech() gate the mock lane only on config and credential presence, never on ENVIRONMENT: `const useMock = mockMode === "on" || (mockMode !== "off" && !canRunReal);` (ai.ts:424, same pattern at 562 and 687). All vision/image/speech models in the seed catalog are provider "google" (the only `task: "vision"` model is gemini-2.0-flash), so in a production deployment where the platform admin has not yet set `google.gemini_key`, every vision feature — Snap-a-Meal, Label Reader, and **lab-extract** — silently runs the deterministic mock and then SETTLES CREDITS for it (`usage = { inputTokens: estUsage.inputTokens, outputTokens: ... }` → `dobj.settle(...)`). Concrete failure: a coach runs /ai/lab-extract on a real client's lab PDF; the mock returns fabricated clinical values (`{ marker: "Vitamin D, 25-OH", value: "22", flag: "low" }`, ai-routes.ts:562-566) which pre-fill the review and can be saved into the client's chart as real lab data — and the tenant is charged credits for it. The `mocked: true` flag is returned in JSON but a grep of apps/app shows no UI surfaces it. Worse for TTS: POST /body-scan/voice-pack without a key generates SILENT WAVs (`silentWav()`), charges the estimated usage (~tens of credits per phrase since `outputTokens: max(200, text.length*12)` at 909k neurons/1M), and caches them permanently in R2/tts_cues — after the key is later configured, the idempotent skip means the tenant is stuck with a paid-for silent voice pack. Round 2 of the prior audit fixed exactly this failure mode for the mock MAILER ("Mock gated on ENVIRONMENT=development; fails closed in prod") but the same hardening was never applied to ai.mock.

**Fix:** Gate the `auto` mock fallback on `ENVIRONMENT === "development"` (mirror the mailer fix): in production, a missing credential should return `{ ok:false, error:"unavailable" }` (fail closed), with `ai.mock=on` remaining an explicit admin override if desired. At minimum, never settle credits on the mock path in production, and delete cached mock TTS cues when a real key is configured.

### H4. No per-client spend cap or rate limit on metered AI endpoints — a single client can drain the tenant's entire credit balance
**Area:** AI Suite — `apps/api/src/ai-routes.ts:155`  
The TenantBillingDO prevents overspend beyond the balance, but nothing bounds how much of the tenant's balance one client persona may consume. Client-callable metered endpoints (/ai/parse-food, /ai/snap-meal, /ai/food-meta, /ai/activity-estimate, /ai/recipe, /ai/narrative, /ai/supplement-guide, GET /ai/coach-note) have zero throttling — the only rate limiter in the codebase is the OTP guard (otp-guard.ts). Concrete failure: a hostile or compromised client account loops `POST /ai/parse-food {clientId: <own>, text: <500 chars>}`; each call reserves and settles real credits against the tenant's shared balance until `insufficient_credits`, draining both the monthly grant AND the owner's purchased (paid-forever) credits, and starving every other client and the coach's own AI tools. The one cache that exists is trivially bypassed: GET /ai/coach-note builds its KV key from `ctx.signalHash`, and `signalHash` hashes `d: today` where `today` is a client-supplied, unvalidated query string (`z.object({ ..., today: z.string().optional() ... })`, ai-routes.ts:947; client-knowledge.ts:508 `d: today`) — so `?today=x1`, `?today=x2`, … each produce a distinct cache key and a fresh paid generation per GET request.

**Fix:** Add a per-user (or per-client persona) daily credit/request budget enforced before reserve (e.g. count ai_generations rows per actor per day, or a KV counter), plus validate `today` as a LocalDate and clamp it to ±1 day of server time so it cannot mint unlimited cache keys.

### H5. client_subscriptions budgets_json/addons_json rewritten by four independent writers with no CAS — concurrent purchase/redeem/grant silently loses paid access days
**Area:** Data Integrity & Concurrency — `apps/api/src/commerce-routes.ts:237`  
The access-economy row is mutated via read-modify-write JSON rewrites from four uncoordinated writers: (1) staff grant — commerce-routes.ts:234-241 reads budgets_json then `UPDATE client_subscriptions SET budgets_json = ?, addons_json = ?, updated_at = ? WHERE id = ?`; (2) client /redeem — commerce-routes.ts:370-393, same pattern (`budgets.push(...); UPDATE ... SET budgets_json = ?`); (3) the Stripe Connect webhook — stripe-routes.ts:755-760 grantClientPackage folds a one-time purchase into the same active row (`.bind(j([...existing, ...added]), ...)`) and renewClientSubscription:811 does the same on every paid cycle; (4) lazy reconcile — commerce-routes.ts:76-86 flips status with `UPDATE ... SET status = 'expired' WHERE id = ?` guarded by neither status nor budgets. None of these carry a WHERE-unchanged guard, unlike the session-completion path which DOES use CAS (`UPDATE ... SET addons_json = ? WHERE id = ? AND addons_json IS ?`, session-routes.ts:114) — and that CAS is itself defeated when one of the non-CAS writers commits a stale addons_json over it. Failure scenario: a client redeems a code (redemption_uses claim + used_count slot are consumed atomically per H5) at the same moment the Stripe webhook lands their one-time purchase on the same active row; the webhook's UPDATE was computed from a read taken before the redeem committed, so the redemption's budget entries are overwritten — days paid for with a burned redemption slot are gone, with no error and no compensation (the /redeem rollback only runs when its own write throws). Similarly, a reconcile racing a /redeem can mark the row 'expired' right after the redeem set it 'active' with fresh budgets, and no read path ever flips expired→active, so the client is locked out of paid features. These are client-device + coach + webhook writers, i.e. genuinely concurrent — unlike the accepted 'plan-body lost-update' residual which was scoped to coach-only editing.

**Fix:** Apply the same optimistic-concurrency pattern already used in session-routes.ts (CAS retry on `budgets_json IS ?` / `addons_json IS ?`) to the grant, redeem, grantClientPackage and renewClientSubscription writers, and guard reconcile with `WHERE id = ? AND status = 'active' AND budgets_json IS ?`. Alternatively move budget appends to a child table (as was done for redemption_uses) so appends are INSERTs, not JSON rewrites.

### H6. Staff (trainer/assistant) invite flow dead-ends: no invitation email is sent and nothing ever accepts the invitation
**Area:** Feature Completeness vs Spec — `apps/api/src/auth.ts:123`  
SPEC §4 requires: 'Trainers/assistants: owner invites by email → invite link → OTP verifies → passkey prompt.' The Better Auth organization plugin is configured as `organization({ ac, roles, creatorRole: "owner" })` with NO `sendInvitationEmail` handler, so `POST /api/auth/organization/invite-member` (called from apps/app/src/screens/coach/Staff.tsx:32, which then shows 'Invite sent to {email}') creates an `invitation` row but delivers nothing. Worse, no code anywhere calls accept-invitation: a repo-wide grep for 'invitation'/'accept' finds only db.ts (table DDL), purge.ts (deletes), and access.ts (a comment) — and the app-side grep for `/api/auth/organization/` finds only `invite-member` and `create`. The context auto-link in context-routes.ts:32-58 links `clients` rows only, never staff invitations. Failure scenario: owner on a Studio plan invites a trainer → UI says 'Invite sent' → the trainer receives no email; even if told to sign in, OTP creates a bare account and they land on Start.tsx ('Ask your coach to invite <email> — your space appears here the moment they do') forever, because the pending invitation is never accepted and no membership is ever minted. Multi-trainer staffing — the product's core premise and what Studio/Team seats are sold for — cannot be onboarded through the app. No integration test covers invite-member → accept either.

**Fix:** Add `sendInvitationEmail` to the organization plugin (branded email with an /accept-invitation/:id deep link), and either an accept-invitation screen or an email-matched auto-accept in the /api/context bootstrap (mirroring the client auto-link). Add a Miniflare test for the full path.

**Area:** Feature Completeness vs Spec — `apps/api/src/session-routes.ts:53`  
SPEC §8.9 (phase 7, claimed built via CLAUDE.md Status 'Foundation through … reports … built and tested'): 'Add-on types (consultations), session scheduling against add-on balances (complete/no-show consume; cancel refunds), assistant role surface. Calendar view.' The API is complete (`GET/POST /addon-types`, `GET/POST /sessions`, `PATCH /sessions/:id` with consume/refund — even hardened in AUDIT round 2), but the ONLY app caller of `/api/sessions` is the read-only client list in apps/app/src/screens/client/Wellness.tsx:103. A repo-wide grep of apps/app/src for `addon-types`, `POST /api/sessions`, or any add-on/session management finds nothing in ClientManage.tsx, Business.tsx, Clients.tsx, or anywhere else; Packages.tsx has no add-on field either, so packages can't include consultation add-ons (SPEC §7 'included add-ons') from the UI. ### H8. No Service Worker or offline write queue — the spec'd offline-first logging PWA capability is entirely absent
**Area:** Feature Completeness vs Spec — `apps/app/vite.config.ts:60`  
SPEC §3 (twice): 'Service Worker + offline write queue for gym-basement logging' and 'offline-first logging (IndexedDB write queue, replay on reconnect)'; SPEC §8.3: 'Offline logging via the PWA write queue.' The app has a manifest (index.html:8 links /manifest.webmanifest, served white-labeled by the worker) but no service worker at all: grep for `serviceWorker`, `registerSW`, `workbox`, `vite-plugin-pwa`, and `indexeddb` across apps/app returns nothing, vite.config.ts registers only react/tailwind/mediapipeWasm plugins, and apps/app/public contains only icon.svg, manifest.webmanifest, and models/. ### H9. Local-date shift helpers mix local parse with toISOString(): all shifted dates are off by one day for every user east of UTC
**Area:** Frontend Correctness — `apps/app/src/screens/client/Today.tsx:30`  
Four copies of the same helper do `const d = new Date(`${date}T00:00:00`); d.setDate(d.getDate() + delta); return d.toISOString().slice(0, 10);` — the parse is LOCAL midnight but the output is the UTC date. For any UTC+ timezone (Europe/Africa/Asia/Australia — e.g. UTC+3, where the ByShujaa model market lives), local midnight of `date` is 21:00 the PREVIOUS day in UTC, so every result is shifted back one extra day. Concrete failures: (1) Today.tsx:187 `setDate((d) => shiftDay(d, -1))` — the 'Previous day' arrow jumps TWO days back, and Today.tsx:194 `setDate((d) => (d < today ? shiftDay(d, 1) : d))` — the 'Next day' arrow is a NO-OP (shiftDay(d, +1) returns d itself), so a UTC+ user paging back through their diary can never page forward again except via 'Jump to today'. (2) Train.tsx:73 `Array.from({length:7}, (_, i) => shift(today, -(6 - i)))` builds the 'this week' window as [today-7 … today-1], so TODAY'S logged sessions and activities (date_local = today) are excluded from the weekly Training Load / tonnage / active-days grid — a client finishes a workout and the week metrics don't move. (3) Wellness.tsx:143/148 — the check-in week dots and the streak loop (`const d = shift(date, -i)`; i=0 yields yesterday, not today) never count today's check-in, so the streak reads one short all day. (4) CoachToday.tsx:250 and Today.tsx:360 — `day === shiftDay(today, -1)` labels the day-before-yesterday group 'Yesterday'. Same buggy helper also at Train.tsx:32, Wellness.tsx:46, CoachToday.tsx:233. Note round 2 fixed exactly this class server-side ('progress week-bucket naked-local date parse') but the frontend copies remain.

**Fix:** Replace `toISOString().slice(0,10)` with local formatting (the same year/month/day padding used by todayLocal() in api.ts), and extract ONE shared shiftDay into api.ts or @kova/domain instead of four drifting copies.

### H10. Connect webhook trusts attacker-controllable metadata: no event.account-to-tenant verification and tenant-unscoped package lookup allow cross-tenant free package grants
**Area:** Money Paths (Billing/Stripe/Credits) — `apps/api/src/stripe-routes.ts:411`  
The Connect webhook grant handlers never check that the connected account the event came from (`event.account`) belongs to the tenant named in the metadata. `payment_intent.succeeded` does: `if (m.kova_client && m.kova_package && m.kova_tenant) { await grantClientPackage(c.env.DB, m.kova_tenant, m.kova_client, m.kova_package, pi.id ?? null, null); }` — metadata is taken at face value. `grantClientPackage` then loads the package with `SELECT budgets_json, addons_json, flags_json FROM packages WHERE id = ?` (no `tenant_id` filter) and inserts a `client_subscriptions` row for the metadata-supplied tenant/client. A Connect `standard` account is a full Stripe account the tenant controls (own dashboard + API keys), and the Connect webhook endpoint receives events for ALL connected accounts. Attack: a user who is a client in victim tenant B onboards their own tenant A with a connected account (self-serve via /connect/onboard), then uses their own Stripe keys to create and pay a $0.50 PaymentIntent on their own account carrying metadata kova_tenant=B, kova_client=<their client id in B>, kova_package=<B's premium package id>. The signature-verified webhook fires and grants them B's package — full budget days, add-ons, and flags — with the victim tenant receiving nothing. The refund/dispute branch even maps `event.account` to a tenant via `tenant_settings.stripe_account_id`, so the mapping exists but the grant branches (checkout.session.completed at line 401-410, payment_intent.succeeded at 411-420, invoice.paid renewals) don't use it. Secondary: `checkout.session.completed` uses `m.kova_tenant!` — a missing tenant key binds `undefined` into D1, which throws, unmarking the event so Stripe retries the poisoned event forever.

**Fix:** In every Connect grant branch, resolve the tenant from `event.account` via `tenant_settings.stripe_account_id` and require it to equal `m.kova_tenant` (drop the event otherwise); also scope the package lookup in grantClientPackage with `AND tenant_id = ?`. Replace the `m.kova_tenant!` assertion with an explicit guard.

### H11. Platform subscription lifecycle keyed only by customer: plan upgrade creates a second parallel Stripe subscription (double monthly charge) and the stale sub's deleted/past_due events downgrade the tenant's live plan
**Area:** Money Paths (Billing/Stripe/Credits) — `apps/api/src/stripe-routes.ts:629`  
Neither /billing/checkout-plan nor /billing/plan-intent checks for or cancels an existing platform subscription — each creates a brand-new Stripe subscription. A tenant on Solo (sub A) who upgrades to Studio gets sub B; A keeps billing, so the tenant is charged $29 + $79 every month. Worse, the lifecycle handlers resolve the tenant by customer only, never comparing the event's subscription id to the stored `stripe_sub_id`: `case "customer.subscription.deleted": { const tenantId = await tenantByCustomer(db, obj.customer as string); if (tenantId) await db.prepare("UPDATE subscriptions SET status = 'canceled', plan_id = 'free' WHERE tenant_id = ?")... }`. So when the owner (or the platform admin) cleans up the duplicate sub A in the Billing Portal, its `customer.subscription.deleted` event drops the tenant to `free`/`canceled` even though sub B is active and paying — the tenant is charged $79/mo while entitlements clamp to free until the next sub-B event happens to re-activate them. `syncStripeSubscription` (line 644) has the same flaw: a `past_due` update on the stale sub marks the whole tenant past_due and starts the dunning clock while the real sub is current.

**Fix:** On plan change, update the existing Stripe subscription's price (or cancel the old sub after the new one activates). In `customer.subscription.deleted` and `syncStripeSubscription`, ignore events whose `obj.id` does not match the tenant's stored `stripe_sub_id`.

### H12. grantMonthly keyed only by calendar month: a mid-month plan upgrade grants zero credits until the next month
**Area:** Money Paths (Billing/Stripe/Credits) — `apps/api/src/billing-do.ts:222`  
`grantMonthly` is a no-op whenever the period key was already stamped: `const last = await this.ctx.storage.get<string>("lastGrantKey"); if (last === periodKey) return this.view();` and every grant path passes the calendar month `periodKey()` ("YYYY-MM"). The daily cron (index.ts:136-142) grants each active paid tenant on the 1st, stamping lastGrantKey for the month. Scenario: tenant on Solo (500 credits, stamped "2026-07" on July 1) pays to upgrade to Studio on July 10. `activatePlan` → `dobj.grantMonthly(2500, periodKey())` (stripe-routes.ts:679) early-returns because lastGrantKey === "2026-07". The tenant is charged the Studio price immediately but keeps only the residual Solo grant until August 1 — a paid-but-not-granted state with no error anywhere. The admin comp route (billing-routes.ts:174) hits the same no-op when moving a tenant to a bigger plan mid-month.

**Fix:** Include the plan id in the grant key (e.g. `${periodKey}:${planId}`), or have grantMonthly top the granted bucket up to the new amount when called again in the same period with a larger grant.

### H13. /connect/cancel-subscription unlinks the row even when the Stripe cancel fails — client keeps being charged with no budget top-up and no way to cancel
**Area:** Money Paths (Billing/Stripe/Credits) — `apps/api/src/stripe-routes.ts:366`  
The cancel route swallows the Stripe API result and unconditionally clears the renewal marker: `await stripeCall(cfg.secretKey, `subscriptions/${sub.stripe_sub_id}`, undefined, { connectedAccount: ..., method: "DELETE" }).catch(() => undefined);` followed by `UPDATE client_subscriptions SET stripe_sub_id = NULL, payment_status = 'canceled' ...`. If the DELETE fails (Stripe outage, revoked connected account, transient network error) the Stripe subscription stays live: the client is charged again next cycle, `renewClientSubscription` can no longer resolve any row by that `stripe_sub_id` (the renewal invoice silently grants nothing — money taken, no access), and the app can never retry the cancel because no row with a `stripe_sub_id` remains (route 404s "no auto-renewing subscription"). This is the exact resolve-by-sub-id invariant H6 established, broken on the cancel path; contrast `cancelInstallmentSub` (line 705-715) which deliberately clears the link only after a confirmed cancel. Secondary defect in the same route: it selects `ORDER BY started_at DESC LIMIT 1`, so a client holding two auto-renewing packages can only ever cancel the newest — asking to cancel the older one silently cancels the wrong subscription.

**Fix:** Mirror cancelInstallmentSub: only NULL `stripe_sub_id`/mark canceled after the Stripe DELETE succeeds (return 502 otherwise so the client can retry). Accept an optional subscription/row id in the body and cancel that specific row.

### H14. Stripe API version unpinned while handlers depend on pre-Basil field shapes (invoice.subscription, latest_invoice.payment_intent) — on a newly created Stripe account Connect renewals silently never grant and inline plan checkout breaks
**Area:** Money Paths (Billing/Stripe/Credits) — `apps/api/src/stripe-routes.ts:424`  
`stripeCall` (stripe.ts:42-62) sends no `Stripe-Version` header, and webhook payload shape follows the endpoint's/account's default API version — for accounts created after 2025-03-31 that is the Basil series, which removed `invoice.subscription` (moved under `invoice.parent.subscription_details`) and removed `invoice.payment_intent` (replaced by `invoice.payments`/`confirmation_secret`). The Connect renewal path reads the legacy field: `const inv = event.data.object as { subscription?: string; billing_reason?: string }; if (inv.subscription && inv.billing_reason === "subscription_cycle") { await renewClientSubscription(c.env.DB, inv.subscription); }` — on a Basil-shaped payload `inv.subscription` is undefined, so every monthly renewal charge succeeds at Stripe while the client's budget is never topped up (silent, recurring paid-but-not-granted). Likewise /billing/plan-intent relies on `"expand[0]": "latest_invoice.payment_intent"` and `sub.latest_invoice?.payment_intent?.client_secret` (stripe-routes.ts:146-156), which does not exist under Basil, so inline plan purchase fails for any platform account on the current API version. Nothing in the code or config pins the version, so correctness depends entirely on when the Stripe account was created.

**Fix:** Pin a tested API version: send a `Stripe-Version` header in stripeCall and create/configure webhook endpoints at that version (or update the handlers to read `invoice.parent.subscription_details.subscription` and use `confirmation_secret`, with legacy fallbacks).

### H15. White text/icons on solid domain-tone backgrounds fail contrast in dark mode — screens bypass the system's --tone-foreground
**Area:** UI / Design-System Consistency — `apps/app/src/screens/client/WorkoutPlayer.tsx:991`  
The token system deliberately inverts domain tones per mode (dark UI: --activity: oklch(0.78 0.13 164), --cardio: oklch(0.74 0.13 250), --success: oklch(0.76 0.14 158), --nutrition: oklch(0.8 0.13 68) — all LIGHT colors) and provides --tone-foreground for text on solid tones (tokens.css:99-104: "a brand `--primary-foreground` can't [clear AA], since its polarity is fixed"). shell.tsx BottomTabs (line 56) and the Shell ambient pageVars (Shell.tsx:186-188) use it correctly. But several high-traffic client surfaces hardcode white on solid tones, which is ~1.6-2.1:1 in the default dark theme (fails AA 4.5:1 for text and 3:1 for icons): WorkoutPlayer.tsx:991 RestTimer chip `done ? "bg-activity text-white" : running ? "bg-cardio text-white"` (the countdown digits every rest, every set); WorkoutPlayer.tsx:188 `bg-activity ... text-white` "Recommended" badge; WorkoutPlayer.tsx:301 `bg-activity text-white` completed-step number; MealPlanDrawer.tsx:353 `border-nutrition bg-nutrition text-white` logged check and :443 `bg-nutrition ... text-white` "Logged" badge; TodayAgenda.tsx:181 `bg-success text-white` completion check; LogSheet.tsx:225 activity picker chip `style={on ? { background: toneVar.cardio, color: "#fff" } : undefined}` — the only raw hex color in any screen, and the selected sport label becomes near-unreadable in dark mode. (White over black image scrims in Train/Explore day cards is fine — those sit on a fixed dark gradient.)

**Fix:** Replace `text-white`/`#fff` with `text-[var(--tone-foreground)]` (or add a `toneSolid` map next to toneSoft/toneVar in primitives.tsx exposing `bg-<tone> text-[var(--tone-foreground)]` pairs) so on-tone text inverts with the tone. The LogSheet chip should also use the shared Chip primitive or the new map instead of an inline style.

## Medium (33)

### M11. ensureSchema migration path swallows ALTER failures and has no versioning — a transiently failed column migration silently 500s writes for the isolate's lifetime
**Area:** Data Integrity & Concurrency — `apps/api/src/db.ts:309`  
Schema evolution on deployed D1 is `for (const sql of alters) await db.exec(sql).catch(() => undefined);` — the catch is meant to swallow 'duplicate column' errors, but it equally swallows real failures (D1 timeout/transient error). Failure scenario: on a cold isolate, `ALTER TABLE food_entries ADD COLUMN target_calories REAL` fails transiently; schemaReady still resolves, and every POST /logs/food (which explicitly lists target_calories in its INSERT, log-routes.ts:442) returns 'no such column' 500s until the isolate is recycled — with no signal that a migration was skipped. Structural risks compound this: there is no schema-version marker, so every cold start of every isolate replays ~110 DDL statements, ~45 ALTER attempts (each an error round-trip once applied) plus the measurements backfill UPDATE (db.ts:315-327); and any future migration expressed as a CREATE UNIQUE INDEX inside the main `.exec()` batch that conflicts with existing rows would throw the whole exec, null schemaReady, and hard-fail every request in a retry loop (the idx_exercises_source recreate is safe only because it is strictly more permissive — the comment acknowledges the hazard).

**Fix:** Distinguish 'duplicate column' from other errors before swallowing (inspect the message), or record applied migrations in app_config/a schema_migrations row so alters run once and a real failure surfaces. Longer term, move to wrangler d1 migrations.

### M26. budgets_json read-modify-write races across /redeem, /subscriptions/grant, and webhook renewal lose paid-for budget days
**Area:** Money Paths (Billing/Stripe/Credits) — `apps/api/src/commerce-routes.ts:376`  
Three writers mutate a client_subscriptions row's `budgets_json` with unguarded read-then-write: `/redeem` (`const budgets = parseJson<Budget[]>(current.budgets_json, []); budgets.push(...); UPDATE client_subscriptions SET budgets_json = ?`), `/subscriptions/grant` (commerce-routes.ts:234-241), and `renewClientSubscription` (stripe-routes.ts:782-811). `/subscriptions/grant` and `/redeem` select the latest active row WITHOUT excluding `stripe_sub_id` rows, so both can land on the same recurring row a Connect `invoice.paid` renewal is updating. Scenario: the monthly renewal webhook fires while the client redeems a code — both read the same budgets_json, both write an absolute value; last writer wins and either the paid renewal period or the redeemed days vanish. On the /redeem side the loss is compounded: the compensation block only runs when the UPDATE throws, so a silently lost update leaves the redemption slot consumed (`used_count` incremented, claim row held) with no days granted — the client can never retry. **Fix:** Apply the H3 pattern: `UPDATE ... SET budgets_json = ? WHERE id = ? ### M27. Free-grant promo paths consume the redemption slot with no compensation if the grant fails — slot burned, nothing granted, retries permanently rejected
**Area:** Money Paths (Billing/Stripe/Credits) — `apps/api/src/stripe-routes.ts:104`  
Both 100%-discount paths consume the promo slot before granting and never release it on failure. /billing/pack-intent: `if (amount <= 0) { if (!promoId || !(await consumePromoRedemption(c.env.DB, promoId))) return ...; const dobj = c.env.BILLING...; await dobj.topUp(pack.credits, "pack.promo", pack.id); }` — if the DO call throws (isolate eviction, transient DO error) the request 500s with `redemption_count` already incremented; on a max_redemptions=1 code every retry now gets `promo_exhausted` and the tenant never receives the credits. /connect/pay-intent (line 321-324) has the identical shape with `grantClientPackage` (a D1 write) as the failable step. ### M28. BETTER_AUTH_SECRET silently falls back to a hardcoded public secret in production

### M29. Client can overwrite another client's workout plan via auto-approved exercise swap (cross-client IDOR write)
**Area:** Security & Tenant Isolation — `apps/api/src/health-routes.ts:444`  
POST /swaps validates only the swap's own client: `const access = await requireClientAccess(c, parsed.data.clientId)` — but `workoutPlanId`, `dayIndex`, `blockIndex`, `slotIndex`, `currentExerciseId`, `suggestedExerciseId` are all attacker-controlled and never tied to that client. The route-guard maps `/api/swaps` to `{ tracking: ['update'] }`, which the `client` role holds (access.ts line 83-88), so a client can call it. When `suggestedExerciseId` forms a bound alternative pair (any tenant-defined pair, `tenant_id = ? OR tenant_id IS NULL`), `autoApprove` becomes true and `applySwap(c.env.DB, access.client.tenant_id, {...d, suggestedExerciseId})` runs immediately. `applySwap` (line 550-569) loads the plan with only `SELECT body_json FROM workout_plans WHERE id = ? AND tenant_id = ?` — no `client_id` check — then does `slot.exerciseId = d.suggestedExerciseId` and writes it back. Failure scenario: malicious client A (belongs to tenant T which has at least one exercise-alternative pair (X,Y)) POSTs {clientId: A_own_id, workoutPlanId: B_plan_id, dayIndex, blockIndex, slotIndex, currentExerciseId: X, suggestedExerciseId: Y}. requireClientAccess(A_own_id) passes (own record), the pair (X,Y) auto-approves, and applySwap silently rewrites the targeted slot of client B's published workout plan to exercise Y. **Fix:** In POST /swaps, after requireClientAccess, load the target plan and reject unless it belongs to access.client.id (e.g. `SELECT client_id FROM workout_plans WHERE id = ? AND tenant_id = ?` and require it equals access.client.id). Better: have applySwap take the expected clientId and scope the SELECT/UPDATE with `AND client_id = ?`.

## Dimension summaries

**Security & Tenant Isolation** — Security & tenant isolation is broadly solid: the three-lane route guard, requireClientAccess (owner/assistant=tenant, trainer=assignment, client=own), custom-domain Host pinning (a stranger to the host tenant gets tenantId=null), media R2 tenant+per-client key scoping, action-OTP scoping, D1 prepared statements everywhere (all `${...}` interpolation is table names from fixed maps or `?`-placeholder lists, no user data in SQL text), and InboxDO user-scoped WS auth all hold. All prior AUDIT.md fixes I could reach are present and un-regressed: isPlatformAdmin fails closed, trainer role carries no org-admin statements, owner-role self-escalation is blocked, redemption is atomic, host cache is invalidated on (de)activation. The one real gap is the exercise-swap surface (health-routes.ts): both the client-facing POST /swaps (auto-approve path) and the staff PATCH /swaps/:id apply an exercise swap onto a workout plan whose ownership is never checked against the swap's client — a cross-client plan-tampering IDOR (High) plus a trainer-assignment-scope bypass (Medium). Fixing both is a matter of validating the plan/swap client through requireClientAccess, the same pattern plan-routes.ts already uses.

**Money Paths (Billing/Stripe/Credits)** — Prior money-path fixes all hold: the DO's settle cap + idempotency (H1/H2), mark-after-process webhook dedup (C1), atomic redemption claim with compensation (H5), per-subscription rows keyed by stripe_sub_id including renewals (H6), replay tolerance, and the guarded AI settle were each re-traced and are present. The core credit meter (TenantBillingDO) and the budget queue/reconcile math are sound. However, the rail is not release-ready: the Connect webhook trusts attacker-controllable metadata without verifying event.account against the tenant (a self-serve cross-tenant paywall bypass), the platform subscription lifecycle is keyed by customer rather than subscription id (upgrades double-bill and stale-sub events downgrade paying tenants), a mid-month upgrade grants zero credits due to the calendar-month grant key, the client-facing cancel route can strand a still-billing subscription, and the unpinned Stripe API version silently breaks Connect renewals on current Stripe accounts. These need fixing before launch; the mediums (platform refund handling, budgets_json races, promo free-grant stranding) should follow shortly after.

**AI Suite** — The core metered loop is sound and all prior fixes in this area hold: settle is capped at the reservation and idempotent (billing-do.ts:168-169), the vision reserve includes IMAGE_TOKEN_EST (ai.ts:296/430), every provider/timeout error path releases the hold, post-success settle failures are swallowed so output is never lost, and stale holds self-reap on a 10-min TTL — I traced all reserve→run→settle/release paths in generate/generateImage/generateSpeech and found no leaked-hold or double-charge route. Context assembly is correctly tenant- and client-scoped (no cross-tenant/cross-client leakage into prompts), structured outputs are id-whitelisted and zod-validated, and the body-scan pipeline recomputes body-fat server-side from bounds-checked inputs with honest null fallbacks. The release blockers are economic/operational rather than plumbing: the mock lane is not environment-gated and in a keyless production deploy silently bills tenants for fabricated meal/label/LAB data (the exact failure mode round 2 fixed for the mailer), and there is no per-client spend cap or rate limit anywhere, so one client can drain a tenant's entire credit balance (with the coach-note cache trivially bypassed via the client-supplied `today` param). I would fix the mock gating and add a spend/rate bound before release; the remaining findings (image dropped on the Workers AI vision path, Gemini safety-stop treated as paid success, three endpoints skipping the per-client AI flags, voice-preview role gap, vision-route media-ACL bypass, prompt-injection hygiene) are important but lower urgency.

**UI / Design-System Consistency** — The design system itself (tokens.css, primitives, overlays, metrics, charts, shell) is genuinely disciplined — oklch tokens throughout, zero raw hex in the UI package, tone maps (toneSoft/toneVar/toneText) used consistently, uniform Reveal+skeleton loading with error EmptyStates and stale-request guards on every major screen, and units formatting almost universally routed through @kova/domain (fmtWeight/fmtEnergy/kgToDisplay etc. — I found no hand-converted unit besides intentional metric-only contexts like the kg plate calculator and coach plan prescriptions). All prior-audit UI fixes verified present: useModalOverlay with focus restore, Field useId, ClientDetail key={clientId}, emoji removal. With the contrast and price findings addressed, this dimension is release-ready.

**Feature Completeness vs Spec** — Overall the build tracks the spec impressively well: the coaching core, nutrition, commerce/access economy, AI v1 + vision suite, content hub, reports, media, custom domains, and the §8.11 experience layer are mostly wired end-to-end, and every prior-audit fix I re-checked in this area (budget all-split, clientFlags requiresFeature loop, swap auto-approve, redemption, retention radar, quota-on-clients, turbo test dependency, feature gating for aiSuite/bfCamera/supplementsLabs) still holds.
